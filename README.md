## Практические проекты

### 1. Интернет-магазин «Сэр Пуэр» — исследовательское тестирование

**Объект:** действующий интернет-магазин китайского чая.

**Методы:** исследовательское и функциональное тестирование, black-box, негативные API-проверки.

**Инструменты:** Chrome DevTools, Postman.

**Цель:** проверить согласованность данных между интерфейсом и сервером, найти и воспроизвести дефекты, оценить их потенциальное влияние на пользователей и бизнес.

#### BUG-002 — Некорректная цена в SEO-метатегах

При проверке SEO-метаданных — области, которую владелец магазина обозначил как проблемную, — обнаружил расхождение между ценой на витрине и ценой в метатегах страницы товара.

Например, у «Жоу Гуй ААА» в метаданных указано **31 800 ₽**, хотя на витрине представлены фасовки **50 г за 1 590 ₽** и **100 г за 3 180 ₽**. Значение в метаданных в 10 раз выше цены за 100 г. Некорректная цена также была зафиксирована в поисковой выдаче.

Для оценки масштаба проблемы использовал вспомогательный Python-парсер, созданный с помощью LLM. Результаты сопоставлял с данными карточек товаров; повторяемость ошибки подтверждена на нескольких позициях. Предположения о причине отделены от подтверждённых наблюдений.

**Методы:** исследовательское тестирование, анализ HTML и метаданных, проверка гипотез.

**Документация:** [BUG-002 — баг-репорт (PDF)](./BUG-002-seo-price-mismatch.pdf) · [Дополнительный анализ товаров (MD)](./prioritet.md)

#### BUG-003 — Обход ограничений фасовки через API

В интерфейсе магазина вес товара выбирается с шагом **50 г**, однако при прямом запросе к `POST /cart/add/` сервер принимает количество, не соответствующее этому шагу.

При проверке через Postman и интерфейс корзины обнаружил возможность добавить некратное значение веса. Для одного из товаров запрос с **316,75 г** привёл к отображению **317 г** в корзине. Проверка другого весового товара также выявила некратное шагу количество.

Основной дефект — недостаточная серверная валидация допустимого шага фасовки. Возможные проблемы при комплектации заказа рассматриваются как риски, а не как подтверждённые последствия.

**Методы:** негативное API-тестирование, анализ граничных значений, сопоставление API и UI.

**Документация:** [BUG-003 — баг-репорт (PDF)](./BUG-003-cart-quantity-validation.pdf)

### 2. SauceDemo — тестирование формы авторизации

**Объект:** [SauceDemo](https://www.saucedemo.com/)

**Функциональность:** авторизация пользователя.

**Методы:** функциональное тестирование, позитивные и негативные сценарии.

Подготовил два тест-кейса для проверки работы формы входа:

| ID | Сценарий | Тип |
| --- | --- | --- |
| TC-001 | Успешная авторизация с корректными данными | Позитивный |
| TC-002 | Авторизация с пустым паролем | Негативный |

В тест-кейсах описаны предусловия, шаги и ожидаемые результаты. Проверяются успешный вход, переход в каталог, обработка незаполненного обязательного поля и сообщение об ошибке.

**Документация:** [Открыть тест-кейсы TC-001 и TC-002 (MD)](./TC-001-002-saucedemo-login.md)
